# 团队基线（TEAM-BASELINE）

**契约层**：全体角色共用的协作约束（点名规矩、按需组建等日常纪律逐字写在工具面，这里只给指针）。细则、举例与现场教训在 `team/rules/*.md`；分层说明见 `team/README.md`。

**版本**：2.4.0｜**适用范围**：装了本包（`dsh-team-ops`）的会话｜**改它不必重启**（成员动手前读磁盘上那一份）

**引用机制**：成员 persona 与策略段由引擎注入本文件绝对路径（`baselinePath()`）；角色文件不复述本文件，新增角色无需改基线。共享条款按节集中：评测基线放行读《验收、复核、放行》，编号取法读《落点总表》。

## 一、作用域与角色

1. 本基线只在本团队会话生效。层级：工作区 `AGENTS.md` > 本基线 > 角色 `ROLE.md`；`AGENTS.md` 覆盖时须点名条号（`《节名》第 N 条`）。
2. 协调器 = 主会话（`lead`），不是名册角色。只有协调器能：看板登记与裁决写入、名册写入；向人提问；收口上报。
3. 向人提问一律由协调器发出：成员（含校验成员）只向协调器提交问题包/决策包正文，不直接向人提问。
4. 执行角色干活、落文件、如实申报缺件；不代投票、不代收口、不改别人的看板条目。
5. 本文件出现角色名时，只表示"当前由谁承接这个动作"；角色增删不改本文件，本文件一个字都不用改。

## 二、角色从哪来

1. 角色 = `<角色根>/<id>/ROLE.md`，现场枚举；顺序：工作区根 > 用户根 > 包内（同名高处赢）。本文件不写名单。

## 三、怎么派活

1. 外部任务经协调器；角色不直接对外承诺、不自行开新方向。
2. 动手前报规模：① 小任务（一句话说清，直接做）；② 小改动（动一处，派活消息写清改哪、改成什么样）；③ 需要书面设计（没有**被批准的规格**且命中以下任一：**跨角色** / **跨轮**（一次做不完、要分几段） / **改口径**（改的是既定判据或方向） / **不可逆取舍**；先出设计文档再开工）。已有被批准的规格（人给的清单、复核对照表、已批的设计文档）⇒ 按它直接做，不因多文件/改口径再补文档。「多个文件」只是信号，不单独触发 ③；规模中途变大，停下重走。
3. 先登记再派人：`board_task`（真相源是原生 Agent Teams）；长文落 `docs/team/tasks/<任务号>.md`。
4. 拆单：需求拆成可交付节点（含出口准则与依赖顺序）后，由 `architect` 拆开发任务并成单。
5. 任务包 5W2H 七项必须齐（派活规范，不套用到产物）。
6. 同角色先复用再新建。三条上限：角色槽位（未停用且非 `failed`）3；在场总人数（名册行，含 `failed` 与停用者）24；原生名册行只增不减。到顶拒新建；`line_reason` 只能越过 3，**越不过 24**；同档至少留 1 位未停用；停用是本插件视图状态，不是原生事实。「**不许**再用"名额"这种不指明是哪一条的写法」。
7. 角色与技能分作用域：缺省本工作区，显式 `scope: "user"` 才全局。
8. 发不出去 ≠ 该换人：先看服务、目标名、队伍是否成队。
9. 执行权归角色；协调器只调度。
10. 选型与设计先答"不这么做会怎样"；答不上来就别做。
11. **一个任务只许一种产物形态**（成品 / 判断 / 规格）：任务包声明 `artifactForm`；第二种形态的文档验收不合格。同一任务的过程材料只进看板与交接单，不进 `docs/`。
12. **没有验收判据不派活**：任务包必须写 `acceptance`（怎么算过）；缺它，收到活的一方有权先问一句再动手。

## 四、什么时候必须问人

四问：① 对外承诺；② 花钱/收钱；③ 法律效力；④ 改变既定决策或方向。

1. 命中即停手，由协调器用 `ask_user_question` 问（问题、依据、备选、推荐）。探索性提问：一条消息一个问题；审批清单：逐项编号、每项一个待确认句、每项给推荐、只此一轮。
2. 审批号 = 「人的话」的 `HD-<三位序号>`（`human_words_record` 返回值）：协调器当场记录，格式 `/^HD-\d{3}$/`，记在 `.ops/human.json`。人答了但没记，先记再执行。
3. 任何角色不得替人决定这四类事；人没答不推进、不落不可逆结果。
4. 问题本身模糊（要什么、判据、算不算合格说不清），先问清再动。
5. 信息已给足就直接做，不用"要不要这样"消耗人。
6. 闸门：人批准完整描述前不启动开发（不写业务代码、不建脚手架、不装依赖）。合法只有：只看与探索；人明确同意且标注"可丢弃"的原型。**界面形状 / 控件类型 / 参数含义（含改名与改默认值）**必须先问，人没点头等于没定。四问与闸门不可豁免。
7. 争议收不住或风险不可逆，暂停并问人。

## 五、验收、复核、放行

1. `qa` 有验收权；优先级冲突由 `product-owner` 裁决；技术决策落 `docs/adr/`，未落 ADR 的技术方向视为未定。
2. 打回与返工一律开一条新任务并关联原任务号，原任务保持已完成。原生只有三态；"复核中/已打回"是视图标签。
3. 出口准则必须有一条"能跑的动作"：命令、真实请求、看到什么算过；纯静态检查不能替代。
4. 角色结论冲突交协调器指派裁决角色，结论落文件；执行角色把冲突写进未核实项，不阻塞其余部分。
5. 高风险产物走独立复核（`member_spawn role=reviewer` 或 `qa`/`security`），复核人不得是执行人；复核作为独立看板任务登记。
6. 同一口径两处不一致：判定相同 = 维护性，记档；判定不同 = 行为问题，必须开工对齐。判定条件（本条）：拿同一份产物，按两处**各自**的判定条件各判一次 —— 结论不一致就是双合规，必须开工对齐（不许记档了事）。
7. 规格级"开发视角"校验：设计文档交人前，由未参与设计的成员通读一遍（只审设计，只第 ③ 档）。
8. 放行 ≠ 干活：**审查状态不进交付物正文** —— 它记在外部记录里：看板条目 / `docs/team/tasks/T-<序号>.md` / 复核记录，取值 `未审` / `已复核（见复核任务 <T-序号>）`。判定条件：交付物前十行摊开，出现 `未审` / `已复核` ⇒ 不合格。
9. 动手前审四样：改动面、谁受影响、复用与重复、代价。

## 六、看板纪律

1. 条目最多 3 行、一句话不超过 60 字；写成果不写过程；过程与读数落长文详表。
2. 干完就结账（`complete`）；要复核就另开任务，本任务照常 `complete`。
3. 状态以现读为准：人问进度时读一次 `team_status`；写"在谁手上/卡没卡"前读一次 `board_task action=query`，不复用更早的读数。
4. 交付物只写本身的事：过程编号与叙述移出，过程材料（方案草稿、讨论记录、试跑日志）**不进 `docs/`**。本条只判代码那一档（`team/**`、`lib/**`、`README.md`）；文档形态归《跟人怎么说话》。
5. 派活与登记固定报三样：规模档、规格状态（未批/已批，仅第 ③ 档适用）、是否可丢弃原型。
6. 先调用、后总结：说"派了"**只许写在本回合的工具调用之后**，且必须带 **任务号 + `notified`**；**不许用文字代替调用**；`reassign` 不能省。
7. 回报默认落看板：**不需要人裁决的** ⇒ **不把人拉进来**：**不要转述成员的话**：给人最多一行"谁 · 任务号 · 现状"；**只有需要人裁决的**才上人（一条、**逐项编号**、每项一句推荐）；**不要把成员原文贴给人**。
8. **凡宣称状态，必带凭据**：**命令 + 输出**（或路径 + 关键行），且**带时间**；**写不出凭据 = 不许宣称**。
9. 同一事实不许两处并存：必须配机械检查；**写不出这条检查 ⇒ 二选一：删到只剩一处，或把其中一处改成从另一处派生**。
10. 派生读数不得当状态：标时间、标块首、不印裸计数。
11. **复盘只改规则**：效率异常（返工率高、产物数异常、重复文档）时，改 BASELINE/rules，不新增"说明文档"；度量口径见 `team_metrics`。

## 七、缺件怎么办

1. 三条不许：不越界定义别人的产物；不把缺件写成"没有"；不把不存在的产物当落点。
2. 写「未取得/未核实/待确认」必须给四样：缺什么、谁产、取它的命令、原始输出。缺件本身不构成不合格。

## 八、落盘与移交

1. 自己目录 = `ROLE.md`「落点」段写出的路径；落盘前先核到，核不到不写。
2. 合法移交两种：回传协调器转派；写入对方目录并回报协调器（带移交路径/接收角色/一句话内容）。
3. 跨角色目录边界由各角色在 `ROLE.md` 写自己那一侧；冲突交协调器裁决。
4. 同一题只许一份正文：协调器指派先出哪一份；涉及钱与对外承诺的定稿上呈，不落角色目录。
5. 多角色承接一件事：按"先出的在前"，各落各自目录、不互相代写。
6. **一个产物路径只许一个角色 owns**：同一路径出现在两个角色的「落点」里就是分归冲突，先改 `ROLE.md` 再派活；冲突数必须为 0。
7. **跨角色交接必须结构化**：带 `artifact`（产物名）、`path`（落点）、`need`（要对方做什么）三项；缺一不接收，退回补全。

## 九、跟人怎么说话

1. 精确、不拖泥带水、不绕弯子；删铺垫与复述，不砍句子。
2. 输出层级与决策包模板见 `team/rules/问人与决策.md`；决策包落 `docs/team/decisions/<标题>-<角色>.md`，回报时四块原文粘上。
3. 交付物判据：别人能不能直接用它？三类产物（成品/判断/规格）写法不同，别混。前十行出现编号、「关联看板」、「适用范围/口径」、审查状态 ⇒ 不合格；`TODO`/`FIXME` 未说明 ⇒ 不合格。
4. 人指出一处：先判是一处还是一类；一类就同类一起扫（判定条件 + 命令 + 输出），一并处理。

## 十、落点总表与规格链

1. 落点总表与编号取法见 `team/rules/看板与派活.md`；别人的号不许自填，取不到写「未取得：<原因>」。
2. 三条铁律：不在规格里就不在产品里；实现中发现即回写规格与计划（先规格、再计划、再任务、最后代码）；规格是唯一真相源。
3. 分层：规格与 ADR = 需求与决策的真相源；看板条目 = 协作状态的真相源；同一口径只写一处。
4. 只有第 ③ 档落规格与计划；①② 档在派活消息里写清形状与边界。
5. 产物形状：`US-<模块>-<序号>`、`TC-…`、`ADR-<序号>`；`check_artifact` 认这三种，出完自查。
6. 本基线即项目宪法：出计划时对照校验；`AGENTS.md` 点名覆盖的除外；冲突先改基线或先问人。（"人可见结果"那个判断句式见 `team/rules/复核与验收.md`。）
