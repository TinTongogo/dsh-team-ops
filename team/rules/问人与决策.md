# 问人与决策（细则与举例）

本文件是 `team/BASELINE.md` 的**细则层**：**主要放**长表 / 举例 / 现场教训 / 理由 / 历史沿革（**以及若干规则的本体**）。
**正文给入口与主规则；细则层给本体与细节** —— **要动手就必须读对应细则**，别只看正文那一句指针。

## §三 5b/5c/5d：括号里的解释

 那一类追问不是谨慎，是把沟通成本推给人。**"人没说"的**（形状 / 控件类型 / 参数含义与默认值 / 命名）才要问，见 5d。

## §三 5c 的括号解释

 合法的只有两件：**只看与探索**，以及**人明确同意、且标注为"可丢弃"的快速验证原型**（原型不进发布面、不写完整用例、不追求稳定；
 要从原型继续往下做 ⇒ **当新需求重走本节闸门**）。

## §三 5d 的解释

 人没点头就等于没定，不许"顺手"改。**四问（①–④）与 5c 的闸门不可豁免**：人可以选"跳过提问环节"，跳过的**只是提问**，
 不是闸门；也不能因为"人之前说这个想法不错"就算批准 —— 口头认可只覆盖当时展示的内容。

## §八：输出表 / 决策包模板 / 对齐表

| 场景 | 默认输出 | 展开才看 |
|:--|:--|:--|
| **入口** | 「收到。做 X，预计 Y。」 | 拆解、登记、派发明细 |
| **出口** | 「X 做完了。产物在 `<路径>`。这是啥 / 能干啥 / 哪里不放心。」 | 判据红绿、自查清单、未核实项 |
| **状态** | 第一行 = 看板**三个分栏**各一个数（名字逐字取自分栏名）：`待办 N · 进行中 N · 已完成 N`；有内容时再加一行**卡住** | 从 `team_status` 逐字抄，不自己算 |
| **卡住** | 「卡在 X。三个选项：A / B / C。推荐 A，一句话理由。不做会怎样。」 | 判据原文、覆盖范围 |
| **决策** | 决策包正文（见下） | 背景、依据 |

**决策包**（给人做决定用，一屏写完 **≤20 行**，四块顺序不动）：

```
## 要定什么
<一句话：人要做的那一个决定>

## 选项
A. <一句话>（代价：<一句话>）
B. <一句话>（代价：<一句话>）
→ 推荐 A，理由：<一句话>

## 做错能回退吗
能 / 不能（<一句话>）

## 定了之后
<谁在哪落，一句话>
```

落点 `docs/team/decisions/<一句话标题>-<角色>.md`。**回报时把四块逐字原文粘上**（不许只回一句「已出决策包」）。

**与「回复以交付物开头」这类外部格式要求怎么对齐**（它不改变本节的判据，只影响先说哪一句）：

| 那一刻的"交付物"是什么 | 第一条该是 |
|:--|:--|
| **干完一件事** | 「产物在 `<路径>`：这是啥 / 能干啥 / 哪里不放心。」——**指针就是交付物**（长内容落文件，**不要把产物贴进回复**） |
| **人问状态** | `team_status` 那两行（计数 + 卡住）本身就是那一刻的交付物 |
| **开工回执** | 「收到。做 X，预计 Y。」——**回执就是那一刻的交付物**（还没东西可交） |
| **命中四问** | **那一刻没有交付物可交**：第一条就是那个问题（决策包在前，不是推荐在前） |

**判定条件**：回报的第一行必须能对上上表的一行；把过程叙述、自查清单、看板编号放在第一行 ⇒ **不合格**（那些是记账，见 §八之一）。

## §八：问问题的形状 1–4

1. 〔探索性〕**一条消息只留一个问题**，句尾就一个问句；**不附示例清单** —— 对方说"你随便猜""你觉得怎么好就怎么来"、或明显卡住时，才给一个短清单。
2. **用对方的词**，不用流程黑话；别铺垫流程本身（「我先说明一下我们的流程」这类删掉）。
3. 问题带上**依据**与**一个可被纠正的猜测**（「我猜你要的是 X，因为 Y 一直麻烦你，对吗？」比"你想要什么"有效得多）。
4. **复盘确认环**：某一块理解到能写成 **200–300 字** 的程度，就先把这段复述发出来、**再**问下一块（整场对话里"复述确认"与"提问探索"交替进行）。
 整段里**每一句都要么标「人确认」要么标「我方推测」**，结尾问"哪里错了、漏了什么"。
 **只有标「人确认」的才许当作已定的前提** —— 我方推测写进产物，等于"把人没说过的话写成他说过的"，按 §八之一 不合格处理。

## §八之二：扫描与写法细节

**先分清两件事**（这是"待办自己长"那个入口）：**人指出来的**那一类，**扫描范围**按本节（同类一并扫 + 写成规则）；
**要不要动代码 / 开条目**按 §四.4（**改变行为或人可见结果**才开工；**维护性**（同一判定两处、重复正文）扫完**记档**）。
两条合起来的动作是：**把同类全扫出来、逐条判类别** —— 该改的改，维护性的一并记档（不是"扫到就都要开工"）。
1. **是一类**（同一套写法 / 同一个习惯在别处也会犯）⇒ **同类一起扫**，并给出扫描口径：**判定条件 + 现场命令 + 原始输出**（例：`LC_ALL=en_US.UTF-8 grep -rn '关联看板：' <产物目录>`）；扫出来的实例**一并**处理 —— 别等人第二次说。**适用范围**：这一条管的是**人已经指出来的**那一类（人指了一处、同类一并处理）；**人没点名**的界面 / 控件 / 参数**不在这条里** —— 那类**只许报告、要改先问**（§三 5d）。
2. **然后写成规则**：落到**一处正文**（本基线或对应角色的 `ROLE.md`），并写清"什么算合格"的**判定条件** —— 下一轮不看这次对话也不会再犯。
3. **是一处**（确实只此一个实例）⇒ 当场改掉，一句话说明改了什么。
4. **不许做的两件**：只修被指出的那一个实例、当成"这一份的问题"（不许）；把规则只写在对话里（下一个会话读不到）（不许）。
