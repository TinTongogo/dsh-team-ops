# 交付物怎么写（细则与举例）

本文件是 `team/BASELINE.md` 的**细则层**：**主要放**长表 / 举例 / 现场教训 / 理由 / 历史沿革（**以及若干规则的本体**）。
**正文给入口与主规则；细则层给本体与细节** —— **要动手就必须读对应细则**，别只看正文那一句指针。

## §八之一：定义与三类产物

**交付物 = 下游能直接拿去用的那件东西本身。**
判据只有一句：**别人能不能直接用它？** 不能 ⇒ 那只是**回报**或**记账**，不是交付物。

- **成品**：代码 / 测试 / 配置 / 数据 / 设计稿 / 对外文案 / 交付出去的界面 —— **程序员交的是可运行的改动（在仓库里），不是《我改了什么》**。
- **判断**：结论 + 依据 —— 评审意见、验收结论、裁决、选型建议。
- **规格**：能拿去执行的东西 —— ADR、需求规格、任务分解单、接口契约、里程碑与出口准则。
- **不是交付物**（这三样是记账，别混进"产出"）：`docs/team/tasks/T-<序号>.md`（交付记录）· 看板条目 · 回报正文（汇报过程与读数的那一段）。
  例：架构师的交付物是 **ADR 与设计文档**（成品就是那几份文件）；开发者的交付物是**他能跑起来的改动 + 验证方式**；"我做了什么、怎么查、分母多少"属于**交付记录**，写在回报与详表里。

**三类产物写法不同，别混**：**交付物**（上面的定义）／ 给系统看的**状态文件**（看板、名册、邮箱）／ 给流程看的**剧本**（任务包、移交字段、决策包）。
下面的写作规则管**所有"给人看的文档形态交付物"** —— **包括 `docs/team/**` 下的判断类文档**（复核记录、验证记录、对照表都算），
**不限路径**；代码与配置按它自己领域的规矩（可运行、可测，**注释口径在代码类角色的检查表里**，见 §五.4 与 §五.5）。
**判定面（可当场核）**：文档形态的产物一律走本节这条判定条件（前十行出现编号 / 审查状态 ⇒ 不合格），
**不许**拿 §五.4 那个 `team/**`、`lib/**`、`README.md` 的清单来放过它 —— 那份清单只管**代码那一档**。

## §八之一：写作规则 1–6 的说明

1. **第一行是标题，第二行起就是读者要的内容**。标题与正文之间**不许**插任何块（引用块 / 分隔线 / 声明 / 自述）。
2. **不写这四类**（它们是系统坐标，不是内容）：
   - **内部编号**：`T-` / `MB-` / `M-`、角色 id；
   - **协作坐标**：承接谁、见哪一份、上一份的链接；
   - **流程引用**：「见 T-0XX 的落地清单」这种（要引就引**产物路径 + 定位**）；
   - **适用范围与口径声明**、方法论自述、状态自述（「本文只做两件事…」「状态：…」）—— 其中**审查状态**（`未审` / `已复核`）
     按 §四.5 记在**外部记录**里，**不进正文**。
3. **确实必要的信息**（来源 / 口径 / 不确定性 / 免责）⇒ 放**文末**一小节，标题写清它是什么；**同一口径全文只写一处**。
4. **长度按"读者要做的那个判断"给**，不按"我这轮干了多少"给：删掉的是铺垫、过程与已经说过的内容，不是把句子砍短。
5. **交付文档不是记账页**：过程与读数进交付记录（看板条目 / `docs/team/tasks/T-<序号>.md`），不进文档正文；看板编号是**系统坐标**，它属于回报，不属于产物。

6. **交付物里不许留临时修复**：`TODO` / `FIXME` /「以后再说」/「后续优化」/「暂不处理」都**不是交付** —— 要么找到根因彻底解决，要么在回报里**明说"这条不做、为什么"**（写进未核实项），别把它埋在产物里等人踩。
