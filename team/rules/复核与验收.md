# 复核与验收（细则与举例）

本文件是 `team/BASELINE.md` 的**细则层**：**主要放**长表 / 举例 / 现场教训 / 理由 / 历史沿革（**以及若干规则的本体**）。
**正文给入口与主规则；细则层给本体与细节** —— **要动手就必须读对应细则**，别只看正文那一句指针。

## §四 1b：出口准则的解释

   `qa` 验收时**拿不到这条动作的原始输出就不放行**。纯静态检查（lint、单测、类型检查）不能替代它 ——
   "各自都完成、合起来跑不起来"是这类项目最常见的翻车点，而它只有真跑一遍才看得见。

## §四 3：值得复核的清单

   值得复核的：安全 / 权限类设计与评审、ADR、发布放行门禁、测试计划与出口准则依赖的关键产物、AI 评测基线与合规产物。**其余情形一律不设复核前置。**

## §四 4：现场教训与判断句式

4. **发现不等于开工**（现场教训：复核每轮都能找出东西，而"每条都开一条任务"会让待办自己长下去）：
   只把**改变行为或人可见结果**的发现开成任务；**维护性**（同一判定有两处、重复正文）、**措辞**、
   **已知天花板**类发现**记进文档**（验证记录里写清"记录不做"+判据），不改代码、不开条目。
   判断句式：这条修的是"人看到的东西会变"，还是"以后改起来省点事"？只有前者值得开工。

## §四 3b：三类问题的细节

   先让一名**没参与这份设计**的成员站在"资深开发"的立场通读一遍，把问题分三类：**① 已解答**（对话或背景里已有答案 ⇒ 直接补进文档）；
   **② 次要细节**（资深开发可自主决定、不影响成品 ⇒ 由校验者定，并在文档里**标注"这是独立决策"**）；
   **③ 必须人确认**（只有人能答、且答案会改变成品形态）。③ 类按**审批 / 确认清单**那一档整理（§三.1）：
   **逐项编号、每项一个待确认句、每项给推荐**、按重要性从高到低排，**只此一轮**；
   **这条清单由协调器发出**（校验成员**只提交问题包正文**，不直接向人提问 —— 与 §一.2 同口径）。
   交付文档时**附一份"我自主决定的清单"**，让人一眼核对。没有可用的独立成员时，协调器自己站这个视角通读一遍。

## §四 6：动手前先审四样

6. **动手前先审**（与第 3 条的事后复核是**两件事**，别互相替代）：动手前写清四样 —— **改动面**（碰哪些文件）/ **谁受影响**（谁会因此改）/ **复用与重复**（能不能用已有的，别写第二份）/ **代价**（时间、体量、风险）。四样写不出来就先别动手。
