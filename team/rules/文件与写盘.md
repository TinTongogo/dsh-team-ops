# 文件与写盘（细则与举例）

本文件是**细则层**（分层说明见 `team/README.md`）：**主要放**长表 / 模板 / 举例 / 现场教训 / 理由 / 错误码。
**正文给入口与主规则；细则层给本体与细节** —— **要动手就必须读对应细则**，别只看正文那一句指针。
不与契约冲突、不重复规则本体（要引就写"见契约《节名》"）；判据以契约为准。

## 同一文件被两人改的展开（本条本体只在细则层，契约层不设条目）

同一文件被两人改：靠机制兜，不靠锁 —— 工具层（`read`/`edit`/`write`）走宿主 fs 服务，三层：
  **原子写 + 按文件串行**（同一文件的两次改动不交错，不会写花）；**版本守卫**（带上"上次观察到的那一版"，
   文件在你观察之后被改过 ⇒ **拒**，报 `FS_STALE_VERSION`）；**`edit` 还要求字面量唯一匹配**
   （内容已变 ⇒ `FS_EDIT_NOT_FOUND` / `FS_AMBIGUOUS_EDIT`，不带版本守卫也拒）；另有 **`dsh-fs-observation-policy`：没读过的文件不许覆盖**。
   被拒的正确动作是 **重读 → 把改动重建在新内容上 → 再试**（**不要原样重写**）。
   **它管不到**：`bash` / 格式化器 / 代码生成器 / 脚本（绕过工具层 ⇒ 没有版本检查）⇒ 那一半靠纪律：
   看板 `write_scopes`（**写具体文件，别写目录**；提示性、不是锁）+ 同一文件**串行派活**（用 `blocked_by`）+
   **协调器看最终 diff 并跑测试** + git **显式列路径**（`git add -A` 会把别人正在写的 WIP 一起提交 —— 现场教训）。

## 写盘面重叠出现之后怎么处置（先判真伪，再四选一）

`write_scopes` 是**声明值**：原生 `writeScopeWarnings`（只比两条都 `in_progress` 的任务）与派活回执的
`risks.write_scope_overlap`（比全部未完成任务）都只是**提示，不是锁** —— 出现重叠时由协调器按下面三步处置，
**不要当成"系统会自己排队"**。

**第一步：判真伪。**
- **真重叠**：两边确实要动同一份文件，或一方目录包含另一方的路径（`src/` 与 `src/a.ts`）。
- **误报**：声明太粗（两边都写目录、实际改不同文件；`src/a.ts` 与 `src/b.ts` 本来就不算重叠）。
  属实才改声明（`board_task edit write_scopes` 改到具体文件）；**不许**为了消警告改成假声明。

**第二步：真重叠，四选一（按推荐顺序）。**
1. **串行化**：后一条加依赖 `board_task set_dependencies`（`blocked_by_tasks: [前一条]`），等前者收口再开工 —— 默认做法；串行后原生告警自然消失。
2. **拆写盘面**：把重叠部分抽成单独一条任务、只由一个人改；两条任务各自声明不重叠的文件或子目录再并行。
3. **合并给一个 owner**：同一文件的多步工序本来就该一个人干 —— `board_task reassign`（已有负责人时带 `handover: true`），另一人不再碰这块。
4. **结构化交接**：用 `handoff` 工具（`to` / `artifact` / `path` / `need`）把写权限与上下文交给同一人，另一人只读或改别处。

**第三步：兜底。** 工具层那三层（原子写 / 按文件串行 / 版本守卫）见上一节；`bash`、脚本、格式化器
**绕不过它们管不到** —— 并行的同一文件若走这些路径，冲突只能靠人发现。所以收口时协调器仍要：
**看最终 diff + 跑测试 + git 显式列路径**。

**不许**：口头约定"先改者完成再改"却继续并行（没有锁，且 `bash` 无守卫）；为了消掉告警把 `write_scopes`
删空或写成不实的更细路径。

## 《缺件怎么办》：缺件的三条不许 + 四样

先分形态：① **读不到**（现场没这个文件）⇒ 写「**未取得：<原因>**」并附取值命令与原始输出；② **没产出**（对方本单未派发）⇒ 同样写「未取得」并把它列进回报的**未核实项**；③ **对不上**（对方定义里根本没这件产物）⇒ 交协调器裁决。

三条不许：**不许越界自己定义别人的产物**（缺件处写「未取得」，不就地补一套）· 不许把缺件写成"没有" · 不许把不存在的产物当落点。

**缺件怎么写才合格**：写「未取得 / 未核实 / 待确认」时必须同时给四样 —— **缺什么**（产物名）/ **谁产**（角色 id）/ **取它的命令**（判定条件原文）/ **原始输出**。四样齐的，缺件本身**不构成不合格**；**缺件只影响依赖它的那几条结论**，其余照常做完、交付、回报。

## 《落盘与移交》：落盘与移交 1–5

1. **自己目录** = 该角色 `ROLE.md` 的「落点（产出与落盘）」那一段逐条写出的路径。落盘前先把「以 X 的 `<路径>` 为准」在 X 的那一段里**核到**，**核不到就不写**。
2. **合法移交只有两种**（都不改自查句语义）：① **回传协调器转派**（产物落自己目录，回报路径 + 一句话摘要）——适用于接收方不明确或要先验收；② **直接写入对方目录并同时回报协调器**——只在对方目录属于该产物类型时可用，回报要带三项字段：`移交路径` / `接收角色` / `一句话内容`。**跨角色移交本身不是违规。**
3. **跨角色的目录边界**：由**涉事角色在自己的 `ROLE.md`「落点」段里各写自己那一侧**（本文件不复述具体路径 —— 那属于角色作业程序）；两边说法冲突 ⇒ 按 《验收、复核、放行》第 4 条 交协调器裁决。
4. **同一题只许有一份正文**：一件事同时落在两个角色的题面上时（谁定稿、谁先出），由**协调器指派先出哪一份**、另一份引它；涉及钱与对外承诺的定稿一律走 《什么时候必须问人》上呈，**不落任何角色目录**。
5. **多个角色承接一件事**：按「**先出的在前**」办（前者的产物是后者的输入），**各落各自目录、不互相代写**。

## 代码与文件里不许出现 emoji / 装饰符号（HD-012 + HD-013）

- **代码与文件里不许出现 emoji 或 Unicode 表情/装饰符号**（人的指令 `HD-012` + `HD-013`「Unicode 表情符号也不允许出现」，**硬规则**）：
   **本仓 tracked 的每一个文本文件**（含 `team/BASELINE.md` 自己、`docs/**`、注释与测试）**都不许带**：
   **emoji 区段**（`U+1F000–1FAFF`）、**`U+2600–26FF`**、**dingbats `U+2700–27BF`**（重对勾 / 对勾 / 重叉 / 叉等），
   以及**变体选择符（`U+FE0F`）/ 零宽连接符（`U+200D`）**；**箭头（`U+2190–21FF`）与常规排版标点（`「」`、`·`、`—`、`（）`）不在其内**。
 **机械检查**：`tests/team-ops.test.mjs` 里那条「全仓扫 emoji / 装饰符号」用例（按**码点**扫 `git ls-files`，
 **失败即红**，报 **文件:行:码点**）—— 规则与检查一对一，别只写规则不写检查（《看板纪律》第 9 条）。

## 《落盘与移交》第 6–7 条：路径唯一归属与结构化交接

- **一个产物路径只许一个角色 owns**：同一路径出现在两个角色的「落点」段里就是分归冲突；由 `role_contract` 交叉校验，冲突数必须为 0。冲突时先改 `ROLE.md`，再派活。
- **跨角色交接必须结构化**：`artifact`（产物名）/ `path`（落点）/ `need`（要对方做什么）三项齐全；缺一不接收，退回补全。禁止用一段叙述代替这三项。
