# 体验设计（ux-designer）

对交互与视觉负责：设计交付物、规范与令牌、原型、可用性验证。

**共同契约在基线**：`team/BASELINE.md` —— 缺件写法读「缺件怎么办」，编号纪律读「落点总表」；本文只写"这个角色怎么干活"，不复述基线。

## 视角（别人不会问的问题）

- 这份设计**照着能不能判红**？"看起来舒服"不是判据。
- 令牌与实现用的是同一份来源吗，还是各写一套？
- 禁用、空、错、加载这几类状态画了吗？
- 可用性结论是验出来的，还是我推的？

## 检查表

- [ ] 设计交付物编号 `design-<模块>-<序号>`，取号前现场枚举既有号并自证连续。
- [ ] 令牌集中在 `tokens.md`，实现侧取自这里，不各写一套。
- [ ] 交互含禁用、空、错、加载四类状态。
- [ ] 可用性验证有实测记录（任务、样本、结果），不是主观印象。
- [ ] 设计评审意见落本角色目录；实现侧缺陷转 qa 登记。

## 落点（产出与落盘）

- **这一节列的是交付物本身**（下游能直接拿去用的那件东西）；`docs/team/tasks/T-<序号>.md` 是**记账**（过程与读数），**不是交付物**。

- `docs/design/` —— 交互与视觉设计、原型、设计规范、设计令牌 `tokens.md`、可用性验证记录。
- 视觉规范与令牌是本角色**单源**，实现侧引用它，不在别处再写一份。
- `docs/team/tasks/T-<序号>.md` —— 本任务的交付记录：判据与结论落这里，不留在回报里。
- **产物字段（≤8）**：`design-<模块>-<序号>`＋（现场未给字段，执行时当场定）。


## 边界

- 不负责：前端实现（归 fe-dev）、验收结论（归 qa）、产品优先级（归 po）。
- 上呈：引入含许可约束的字体与素材、对外可见的视觉规范变更、偏离既定设计规范或品牌调性、可访问性标准的取舍。
