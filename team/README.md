# 团队契约的组织方式（第一性原理）

本目录只做一件事：让"团队怎么协作"有**唯一正文**，且不因使用者身份、角色增减或应用场景而变化。

## 一、为什么分三层

协作信息有两种，混在一起会互相淹没：

- **约束**：必须做 / 不许做 / 怎么判合格。它需要**稳定、可判、全体一致**。
- **解释**：为什么这么定、长表、举例、现场教训、边界案例。它需要**可展开、按需读、允许长**。

把两者写在同一个文件里，结果是：规则被解释淹没，解释被当成规则引用。所以拆成两层契约 + 一层角色作业程序：

| 层 | 文件 | 回答的问题 | 读的时机 |
|---|---|---|---|
| **契约层** | `team/BASELINE.md` | 必须遵守什么、什么算合格 | 开工前对齐；拿不准时 |
| **细则层** | `team/rules/*.md` | 为什么这么定、具体怎么做、边界案例 | 要动手且契约那一句不够时 |
| **角色层** | `team/roles/<id>/ROLE.md` | 这个角色怎么干活 | 扮演该角色时 |

## 二、各层的本质目的

**契约层（BASELINE）**
- 目的：给全体角色一套**可判**的协作约束。
- 内容：作用域、派活、问人、验收复核、看板纪律、缺件、落盘、说话、规格链。
- 边界：**不写**单个角色的作业程序，**不写**长表与举例（那些在细则层）。
- 判定：每条都要能当场核（"什么算不合格"写在条目里）。

**细则层（rules）**
- 目的：展开契约层的一句话，提供**可查**的本体与细节。
- 内容：长表、模板、举例、现场教训、错误码、目录边界。
- 边界：**不与契约冲突**；**不重复规则本体**（要引就写"见契约《节名》"）；不单独构成判定（判据以契约为准）。
- 组织：一个文件一个主题域，与契约层的节对应（看板与派活 / 复核与验收 / 问人与决策 / 交付物怎么写 / 文件与写盘 / 角色与编制）。

**角色层（ROLE.md）**
- 目的：界定**一个职责域**及其作业程序。
- 内容：一句话定位、视角（别人不会问的问题）、检查表、落点（产出与落盘）、边界（明确不做什么）。
- 边界：**只写本角色领域内的事**；不定义其他角色怎么干活；不复述契约；跨角色的分归只写"我的边界之外归谁"这一句，不写对方怎么做。
- 判定：角色文件之间**不互相定义**；分归冲突由契约层《落盘与移交》裁决。

## 三、角色无关性（定位恒定）

三层定位不随以下因素变化：

- **谁在读**：协调器、成员、人，读到的都是同一份契约。
- **角色怎么增减**：契约层不点名角色；角色文件增删不改契约。契约里出现角色名时，只表示"当前由谁承接这个动作"。
- **什么场景**：工作区、用户级、包内角色一视同仁；项目差异由工作区 `AGENTS.md` 按契约层《作用域与角色》点名覆盖，不改契约本体。

## 四、内容组织方式

- **契约层**按**协作生命周期**组织：身份与权限 → 派活 → 问人 → 验收 → 记账 → 缺件 → 落盘 → 说话 → 规格链。
- **细则层**按**主题域**组织，一个域一个文件；域与契约节的对应关系写在文件首行。
- **角色层**按**职责域**组织，一个角色一个目录；角色之间只通过契约层的分归规则发生关系。

## 五、适用条件

- 契约层：**所有角色、所有场景、所有时间**（恒定）。
- 细则层：**按需**——要动手且契约那一句不够、遇到边界案例、需要长表或错误码时。
- 角色层：**扮演该角色时**。

## 六、文件清单

```
team/
  README.md              本说明（组织方式，不是规则）
  BASELINE.md            契约层（唯一权威）
  rules/                 细则层（按主题域）
    看板与派活.md
    复核与验收.md
    问人与决策.md
    交付物怎么写.md
    文件与写盘.md
    角色与编制.md
  roles/<id>/ROLE.md     角色层（只写本角色领域）
```

**引用机制**：成员 persona 与策略段由引擎注入 `BASELINE.md` 的绝对路径；角色文件不复制契约，新增角色不需要改契约。
